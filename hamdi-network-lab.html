01Introduction & objectives

This lab set up a small university-style network in VirtualBox, combining four core server administration skills into one exercise: Active Directory (identity and domain control), a Linux web server (Nginx), a Linux proxy server (Squid) that filters and logs web traffic, and DNS integration — so the whole setup behaves like a real campus network.

The end goal: a domain-joined client logs in with an Active Directory account, resolves an internal website by name using the domain's own DNS server, and only reaches that website — and the rest of the internet — through a proxy server that can allow, block, and log traffic.

  • Set up an isolated virtual network in VirtualBox (Internal Network)
  • Install and configure Active Directory Domain Services on a Windows Server VM
  • Deploy a Linux web server using Nginx
  • Install and configure a Squid proxy server
  • Integrate proxy access with the domain network
  • Apply web access-control (allow/deny) policies on the proxy
  • Test and troubleshoot DNS, web, and proxy connectivity

Four virtual machines, all attached to the same VirtualBox internal network ("LabNet", 192.168.10.0/24):

Every machine — including the DHCP-assigned client — uses DC1 as its DNS server. That single detail is what makes domain join, name resolution, and Active Directory login work correctly.

03Active Directory (DC1)

DC1 was configured with a static IP, promoted to a Domain Controller, and set up as the root of the university.local domain. Domain user accounts were then created for the team.

04Web server (WEB1)

Nginx was installed and enabled on WEB1, and a simple intranet portal page was published for the domain to reach.

05DNS integration

An A record was added on DC1 so the web server resolves by a friendly internal name rather than a raw IP — the same pattern real organizations use for internal tools.

Fig. 5Confirming DNS resolution with ping and nslookup

06Proxy & access control (PROXY1)

Squid was installed and configured so all client web traffic routes through PROXY1. Access-control rules were then added to deny specific sites at the network level — meaning a block applies to every device using the proxy, without touching individual machines.

Fig. 6Squid access-control rules — allow localnet, deny the rest

07Joining the domain (CLIENT1)

CLIENT1 was set to pick up its network settings via DHCP, then joined to the university.local domain so it could authenticate with a domain account rather than a local one.

Fig. 7Joining CLIENT1 to the university.local domain

08Testing & results

Every part of the setup was tested end to end before the lab was signed off:

✓Web server loads— browser displays the intranet portal from WEB1
✓DNS resolves correctly— nslookup returns WEB1's address via DC1
✓Proxy redirects traffic— client requests route through PROXY1
✓Blocked sites are denied— disallowed domains show Squid's access-denied page
✓Logs are generated— access.log records timestamped entries with client IP and site

09Conclusion

This lab combined four previously separate skills — Active Directory, DNS, web hosting, and proxy administration — into a single working network, and showed how much they depend on each other in practice: domain join fails without correct DNS, the friendly portal URL only resolves because of the A record on DC1, and every client request reaches the internet only because it's routed through the proxy first.

The access-control step showed how organizations enforce acceptable-use policy at the network level rather than per machine, and the logging step showed why proxies matter for auditing — every request is timestamped and tied to a client IP, which is exactly the evidence a network administrator would use to investigate misuse or diagnose a connectivity issue.
